# Dr.Lemon 信息聚合AI系统 Production Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 将当前项目从“高频迭代原型”升级为“金融机构可持续使用的生产级信息流平台”，支持稳定采集、可追溯分析、可执行闭环。

**Architecture:** 以“采集层 → 标准化层 → 事件层 → 洞察层 → 执行层 → 治理层”六层架构重组现有能力。先完成 P0 稳定性与审计闭环，再推进 P1 质量提升和 P2 组织化协作。

**Tech Stack:** FastAPI, SQLite/FTS5, local SPA (`static/index.html`), model routing (`app/services/llm_client.py`), multi-source connectors (chatlog/email/media/mp/news/langbot).

## 1. 产品定位与边界

### 1.1 产品定位
- 面向对象：券商研究、买方投研、机构销售与投顾团队。
- 核心定位：多源信息流的“采-析-执”一体化平台，而不是单纯资讯阅读器。
- 核心价值：
  1. 在同一屏处理私域沟通流（微信/邮件）与公网内容流（新闻/自媒体/公众号）。
  2. 输出可追溯结构化观点，而不是一次性文本摘要。
  3. 从观点直接进入发送/任务，形成业务闭环。

### 1.2 非目标（本阶段）
- 不做交易执行系统（OMS/EMS）。
- 不做行情 Tick 级因子研究平台。
- 不做重 BI 报表中台（先做轻量驾驶舱与任务看板）。

## 2. 行业对标与差异化

### 2.1 对标群
- 终端类：Bloomberg Terminal / LSEG Workspace / Wind / Choice / iFinD
- AI 研究类：AlphaSense / Quartr AI
- 开源平台类：OpenBB / FinWorld / FinRobot（研究框架）

### 2.2 你的差异化（建议对外表达）
- “私域消息 + 公域资讯 + 会议纪要 + 发送闭环”四合一。
- 可本地部署，数据与提示词可控。
- 模型路由与兜底可配置，兼顾成本、速度、稳定性。

## 3. 目标用户与关键场景

### 3.1 用户角色
- 基金经理：看主题、方向、仓位线索与风险雷达。
- 研究员：追踪行业/公司证据链，快速形成日报/周报。
- 销售/投顾：提炼客户沟通素材，快速生成个性化触达。

### 3.2 高价值场景（按优先级）
1. 早盘前 30 分钟：自动汇总“昨日收盘后 + 今晨”关键信息并给今日行动。
2. 盘中异动：观点冲突、情绪转向、风险升级的事件提醒。
3. 收盘复盘：观点命中与偏差分析，形成可回溯报告。
4. 客户触达：从观点一键生成“约问答/跟进话术”并进入发送任务。

## 4. 生产化 KPI（北极星 + 二级指标）

### 4.1 北极星指标
- **有效决策提速率**：用户在同等信息量下完成一次“观点形成+行动决策”的平均时长下降。

### 4.2 业务质量指标
- 事件去重率（重复信息压缩比例）
- 观点可追溯率（观点可回查到证据消息/来源的比例）
- 摘要可用率（用户“可直接使用”反馈占比）
- 负面信号召回率（已发生风险事件中的提前命中比例）

### 4.3 工程稳定指标
- 关键链路成功率（采集、摘要、导出、发送）
- P95/P99 响应时延
- 模型通道成功率/超时率/降级触发率
- 日志完备率（report_id 级可追溯）

## 5. 六层能力模型（目标架构）

### 5.1 采集层（Ingestion）
- 微信、邮件、新闻、自媒体、公众号、会议录音/导入统一接入。
- 每个源定义 `source_id / fetch_ts / raw_id / checksum`。

### 5.2 标准化层（Normalization）
- 统一字段：`event_time, actor, channel, content_type, summary, sentiment, tags, urls, attachments`。
- 引入质量标记：`is_spam, is_blacklisted, parse_confidence, summary_origin`。

### 5.3 事件层（Eventization）
- 跨源事件合并（时间窗 + 主题 + 实体 + 地点 + 关键词相似度）。
- 事件主键：`event_id`，并维护 `source_refs[]`。

### 5.4 洞察层（Insight）
- 固定结构报告模板（你已定稿的市场 7 类 + 今日行动）。
- 每条观点附量化侧证：支持/反对/中性占比 + 样本量 + 近期趋势。

### 5.5 执行层（Action）
- 观点 → 任务（提醒/发送/跟进）链路。
- 发送任务结果回写，形成闭环评估。

### 5.6 治理层（Governance）
- 报告审计：`report_id` 关联 `snapshot_id/model_channel/prompt_version/evidence_ids`。
- 配置版本化：提示词、路由、黑白名单、阈值均可回滚。

## 6. 12 周实施路径（不改业务方向，先稳后强）

### Phase P0（第 1-3 周）：稳定性 + 可追溯
- 目标：系统“每天可稳定跑”，且每份总结都能追溯来源与模型。
- 交付：
  1. 统一任务状态机（采集/摘要/导出/发送）
  2. 审计字段落库（模型、提示词版本、证据ID）
  3. 服务守护与健康检查（启动稳定、自动重试、故障降级）
  4. 一页通导出质量标准（版式/颜色/品牌/可读性）
- 验收：
  - 连续 5 天任务成功率 >= 99%
  - 报告追溯率 100%
  - 导出失败率 < 1%

### Phase P1（第 4-7 周）：内容质量 + 投研价值
- 目标：减少噪声，提升观点命中与可用性。
- 交付：
  1. 事件合并引擎 v1（跨源去重）
  2. 情绪分类升级（正/负扩展到方向+置信度+争议度）
  3. 量化侧证模板固化（模块级统计）
  4. 提示词 AB 测框架（按模块评估）
- 验收：
  - 去重压缩率显著提升（目标 > 30%）
  - 用户可用率（人工标注）提升
  - 风险召回率可被量化追踪

### Phase P2（第 8-12 周）：组织化使用 + 商业化能力
- 目标：从“个人效率工具”升级为“团队协作平台”。
- 交付：
  1. 角色化视图（基金经理/研究员/销售）
  2. 模板中心（提示词、报告模版、发送策略）
  3. 团队权限与日志（最小可用 RBAC）
  4. 自动日报/周报与订阅推送
- 验收：
  - 团队级活跃稳定
  - 报告产出时间下降
  - 复用模板占比持续上升

## 12. 巡检脚本与验收脚本清单（先定义，不立即编码）

1. 关键链路端到端：拉取→总结→导出→发送（全链路通过）

   - 断开主模型通道

1. 7天关键链路成功率 >= 99%
2. 关键接口 P95 时延达标（非LLM < 3s）

4. 失败任务 100% 可追溯
5. 无“PID在但服务不可访问”假存活问题

## 13. D2 交付：故障分类与归因字典 v1

### 13.1 目标
- 任何一次失败都必须可归因、可重试、可告警、可恢复。
- 前端提示、后端日志、任务状态三者使用同一错误码体系。

### 13.2 错误码格式（统一规范）

格式：`<DOMAIN>-<TYPE>-<NNN>`

- `DOMAIN`（故障域）
  - `SYS`：系统/进程
  - `ING`：数据采集（chatlog/email/media/mp/news）
  - `MOD`：模型调用
  - `RTR`：模型路由
  - `RND`：摘要渲染
  - `EXP`：导出
  - `SND`：发送网关
  - `DB`：数据库/存储
  - `CFG`：配置
  - `NET`：网络/连接
  - `UI`：前端交互
- `TYPE`（故障类型）
  - `TIMEOUT`, `AUTH`, `UNAVAILABLE`, `RATE`, `DATA`, `STATE`, `VALIDATION`, `DEPENDENCY`, `UNKNOWN`
- `NNN`
  - 三位流水号，按域内递增（001-999）

示例：`MOD-TIMEOUT-001`、`EXP-DEPENDENCY-002`、`SYS-STATE-001`

### 13.3 严重级别与响应策略

- `P0`：全局不可用或核心链路阻断（必须立刻告警）
- `P1`：核心能力显著降级（需自动切换并告警）
- `P2`：局部失败可降级（记录并跟踪）
- `P3`：体验/展示问题（聚合修复）

### 13.4 重试与兜底矩阵（总则）

1. `TIMEOUT/UNAVAILABLE/RATE`：可重试（指数退避）
2. `AUTH/VALIDATION`：不可盲重试（需配置修复）
3. `DATA`：重试 1 次后转人工检查
4. `DEPENDENCY`：允许切换备用通道
5. `UNKNOWN`：最多重试 1 次，随后落 `failed` 并强告警

推荐退避：`1s -> 3s -> 7s`，最大 3 次；超限转失败并触发兜底。

### 13.5 标准日志字段（最小集合）

- `trace_id`
- `task_id`
- `module`（market/newswatch/...）
- `route_kind`（main/mid/tool）
- `channel_id`
- `error_code`
- `severity`
- `retry_count`
- `latency_ms`
- `source_key`
- `snapshot_id`
- `prompt_version`
- `recover_action`（retry/fallback/manual）
- `ts`

### 13.6 前端错误展示规范

1. 展示文案必须包含：
  - 用户可理解描述（`human_message`）
  - 建议动作（`recover_hint`）
  - 错误码（便于反馈）
2. 按严重级别展示：
  - `P0/P1`：红色横幅 + 重试按钮
  - `P2`：黄色提示条
  - `P3`：弱提示或折叠日志
3. 禁止仅显示“失败/未知错误”无错误码。

### 13.7 首批故障码清单（v1）

#### SYS（系统/进程）
- `SYS-STATE-001`：PID 存在但端口未监听（假存活）
  - 严重级：P0
  - 可重试：是（重启服务）
  - 兜底：自动切前台常驻/守护重启
- `SYS-UNAVAILABLE-002`：`/api/health` 不可用
  - 严重级：P0
  - 可重试：是
  - 兜底：触发健康自愈流程

#### ING（采集）
- `ING-TIMEOUT-001`：上游拉取超时（chatlog/email/media/mp/news）
  - 严重级：P1
  - 可重试：是（3次）
  - 兜底：跳过本轮，保留上次快照
- `ING-AUTH-002`：上游鉴权失败
  - 严重级：P1
  - 可重试：否
  - 兜底：提示检查 token/账号配置
- `ING-DATA-003`：上游返回结构异常/缺字段
  - 严重级：P2
  - 可重试：1次
  - 兜底：局部丢弃并记录坏样本

#### MOD（模型）
- `MOD-TIMEOUT-001`：模型调用超时
  - 严重级：P1
  - 可重试：是
  - 兜底：切备用模型通道
- `MOD-RATE-002`：429 限流
  - 严重级：P1
  - 可重试：是（退避+降并发）
  - 兜底：降权当前通道
- `MOD-UNAVAILABLE-003`：模型服务不可用/5xx
  - 严重级：P1
  - 可重试：是
  - 兜底：切备用通道
- `MOD-VALIDATION-004`：返回格式不合规（非 JSON/字段缺失）
  - 严重级：P2
  - 可重试：1次
  - 兜底：启用本地规则摘要

#### RTR（路由）
- `RTR-STATE-001`：无可用通道（全熔断）
  - 严重级：P0
  - 可重试：是（冷却后）
  - 兜底：固定兜底模型
- `RTR-DATA-002`：路由配置非法（权重/通道ID异常）
  - 严重级：P1
  - 可重试：否
  - 兜底：回退默认路由配置

#### EXP（导出）
- `EXP-DEPENDENCY-001`：html2canvas 加载失败
  - 严重级：P2
  - 可重试：是
  - 兜底：切纯文本 markdown 导出
- `EXP-RENDER-002`：颜色函数/样式渲染异常
  - 严重级：P2
  - 可重试：是（safeMode）
  - 兜底：降级简版样式导出
- `EXP-DATA-003`：导出内容为空
  - 严重级：P3
  - 可重试：否
  - 兜底：提示先运行分析

#### SND（发送）
- `SND-NET-001`：网关连接中断/远端断开
  - 严重级：P1
  - 可重试：是
  - 兜底：切备用发送通道/入待发送队列
- `SND-VALIDATION-002`：发送参数缺失（目标/机器人/适配器）
  - 严重级：P2
  - 可重试：否
  - 兜底：阻止发送并提示修复
- `SND-STATE-003`：发送回执超时
  - 严重级：P2
  - 可重试：是（1次）
  - 兜底：标记“待确认发送状态”

#### DB（存储）
- `DB-UNAVAILABLE-001`：数据库不可写/锁冲突超时
  - 严重级：P0
  - 可重试：是
  - 兜底：只读降级 + 告警
- `DB-DATA-002`：数据迁移/结构不一致
  - 严重级：P1
  - 可重试：否
  - 兜底：停止写入并提示迁移

#### CFG（配置）
- `CFG-VALIDATION-001`：配置字段非法
  - 严重级：P2
  - 可重试：否
  - 兜底：回退默认值并提示修复
- `CFG-STATE-002`：关键配置缺失（API key/URL）
  - 严重级：P1
  - 可重试：否
  - 兜底：禁用相关模块并提示补全

### 13.8 告警路由（v1）

- `P0`：立即告警（系统通知 + 日志标红 + 首页横幅）
- `P1`：5 分钟内累计超过阈值告警（例如 5 次）
- `P2`：仅记录并进入日报
- `P3`：仅统计，不实时告警

### 13.9 D2 验收标准

1. 任一失败日志均可映射到标准错误码
2. 前端可见错误都带 `error_code`
3. 可重试类错误有统一重试策略
4. `P0/P1` 触发时有明确降级动作
5. 故障复盘可按错误码聚合统计

## 14. D3 交付：任务状态机规范 v1

### 14.1 目标
- 所有异步任务（同步/总结/导出/发送）统一生命周期与可观测语义。
- 避免“表面成功、实际失败”与“无限重试”。

### 14.2 统一状态定义

- `queued`：已入队，等待执行
- `running`：执行中
- `retry`：本次执行失败，等待重试窗口
- `success`：执行成功（终态）
- `failed`：执行失败且不再重试（终态）
- `cancelled`：用户或系统取消（终态）

终态集合：`success / failed / cancelled`

### 14.3 状态流转规则（通用）

1. `queued -> running`
- 触发：worker 拉起任务

2. `running -> success`
- 触发：返回有效结果并通过后置校验（结构完整/字段合法）

3. `running -> retry`
- 触发：可重试错误（见 D2 错误码矩阵）

4. `running -> failed`
- 触发：不可重试错误，或重试次数超上限

5. `retry -> queued`
- 触发：到达下一次退避时间窗口

6. `queued/running/retry -> cancelled`
- 触发：用户取消，或上游依赖被判定不可用且策略要求中断

禁止流转：
- `success -> *`
- `failed -> running`（必须创建新任务）
- `cancelled -> running`（必须创建新任务）

### 14.4 任务公共字段（最小集合）

- `task_id`（全局唯一）
- `task_type`（sync/summary/export/send）
- `status`
- `priority`（high/normal/low）
- `attempt`（当前尝试次数）
- `max_attempts`
- `next_retry_at`
- `error_code`
- `error_message`
- `recover_action`
- `created_at/updated_at/started_at/finished_at`
- `trace_id`
- `payload_hash`（用于幂等）

### 14.5 重试策略（基线）

- 默认：最大 `3` 次（首次执行 + 2 次重试）
- 退避：`1s -> 3s -> 7s`
- 抖动：`±20%` 防止雪崩
- 超上限：转 `failed`
- 不可重试（`AUTH/VALIDATION`）：直接 `failed`

### 14.6 幂等策略（防重复执行）

1. 幂等键：`task_type + payload_hash + time_bucket`
2. 已有 `running/queued` 且幂等键一致：
- 新请求返回已有任务ID，不重复创建
3. 已有 `success` 且仍在有效窗口：
- 直接复用结果（summary/export）
4. `send` 任务额外幂等：
- `target + message_hash + channel + 业务窗口` 防止重复发送

### 14.7 子任务策略差异（按类型）

#### A. 同步任务（`sync`）
- 成功判定：
  - 至少完成一次源读取并写入状态更新（可为0增量）
- 最大重试：
  - `TIMEOUT/UNAVAILABLE` 最多 3 次
- 失败终态：
  - 上游认证失败（`ING-AUTH-*`）立即失败
- 兜底：
  - 保留上次快照 + 标记“数据可能滞后”

#### B. AI总结任务（`summary`）
- 成功判定：
  - 目标模块均返回可渲染内容（或按模块降级）
- 最大重试：
  - 模型类错误最多 3 次，跨通道重试优先
- 失败终态：
  - 无可用模型通道（`RTR-STATE-001`）且兜底失败
- 兜底：
  - 回退缓存/本地规则摘要

#### C. 导出任务（`export`）
- 成功判定：
  - 生成文件成功并可下载
- 最大重试：
  - 渲染类错误最多 2 次
- 失败终态：
  - 内容为空或依赖不可用且降级失败
- 兜底：
  - 海报失败 -> 简版样式导出 -> markdown 导出

#### D. 发送任务（`send`）
- 成功判定：
  - 网关返回发送成功回执（或可验证消息ID）
- 最大重试：
  - 网络类最多 2 次
- 失败终态：
  - 参数校验失败、目标无效、鉴权失败
- 兜底：
  - 入“待确认发送队列”，人工二次确认

### 14.8 优先级与调度

- `high`：手动触发（用户可见链路：发送、导出、当前页总结）
- `normal`：定时总结与常规同步
- `low`：历史补算、低峰清理任务

调度规则：
1. 同类型并发上限（避免抢占）
2. 高优先级可抢占低优先级 `queued`
3. 同一用户会话的交互任务优先

### 14.9 取消策略

- 用户取消：
  - `queued/running/retry` 可取消，状态置 `cancelled`
- 系统取消：
  - 依赖故障且策略要求停机保护时批量取消低优先级任务
- 取消后处理：
  - 必须写入取消原因与触发方（user/system）

### 14.10 任务结果保留与清理

- `success` 结果保留：
  - summary/export：建议 7-30 天
  - send 回执：建议 30-90 天
- `failed/cancelled` 保留：
  - 至少 30 天（用于复盘）
- 清理策略：
  - 按状态与时间分层清理，避免影响审计链路

### 14.11 状态机验收标准（D3）

1. 任一任务都能明确进入终态（不允许长期悬挂）
2. 可重试任务的 `attempt/max_attempts` 可观测
3. 不可重试错误不会重复抖动重试
4. 幂等请求不会产生重复发送/重复总结
5. 前端可看到任务状态与最近错误码

### 14.12 D4 输入（为下一步做准备）

本节输出将作为 D4“启动与保活方案”输入，重点使用：
1. 任务优先级与并发上限
2. 失败终态定义
3. `retry -> queued` 的调度触发规则

## 15. D4 交付：启动与保活方案 v1

### 15.1 目标
- 解决“进程看似启动但端口不可用”的假存活问题。
- 在故障场景下实现自动恢复、可回退、可观测。
- 将“启动成功”定义为健康可达，而不是仅有 PID 文件。

### 15.2 启动成功判定（新标准）

启动成功必须同时满足：
1. 进程存在（PID 有效）
2. 端口监听（`127.0.0.1:8001`）
3. 健康接口返回 200（`/api/health`）
4. 核心配置加载成功（无 `CFG-VALIDATION-*`）

任一条件不满足均视为启动失败，触发恢复流程。

### 15.3 保活分层（推荐架构）

#### 第 1 层：进程守护（OS 级）
- macOS：`launchd`（推荐）  
- Linux：`systemd`（推荐）  
- 容器：`restart: always` + 健康检查

职责：
1. 进程异常退出自动拉起
2. 启动失败限制重试频率（防止重启风暴）
3. 记录最近 N 次退出原因

#### 第 2 层：应用自检（App 级）
- 启动前检查：
  - 配置合法性（`CFG-*`）
  - 数据库可写性（`DB-*`）
  - 关键路径可访问性（日志目录、静态资源）
- 启动后检查：
  - 健康探针
  - 关键接口冒烟（配置、列表、AI配置）

#### 第 3 层：任务保活（Worker 级）
- 任务队列卡死检测（running 超时）
- 自动重置策略（超时任务 -> retry/failed）
- 防重复恢复（依赖 `payload_hash`）

### 15.4 自愈流程（状态机）

1. 发现异常（health fail / 端口未监听 / 关键错误码）
2. 首次恢复：优雅重启（graceful）
3. 二次恢复：强制重启 + 清理僵尸 PID
4. 三次失败：进入降级模式（只读/只展示缓存）并触发 P0 告警
5. 人工介入后恢复正常模式

### 15.5 启动脚本规范（脚本层）

脚本必须具备：
1. `start` 后阻塞等待健康成功（超时即失败）
2. `status` 输出三态：
  - running+healthy
  - running+unhealthy（高风险）
  - stopped
3. `restart` 包含：
  - 旧 PID 校验
  - 僵尸 PID 清理
  - 端口占用冲突检测
4. `logs` 默认显示最近启动失败片段

### 15.6 “假存活”专项治理

问题定义：
- PID 文件存在，但进程已退出或端口未监听。

治理动作：
1. PID 校验改为“PID + 端口 + health”三重校验
2. 写 PID 前后加原子校验（避免竞争条件）
3. 启动后 N 秒内连续探测 health
4. status 命令显式报告 `SYS-STATE-001`

### 15.7 关键探针与巡检

#### liveness（存活）
- `GET /api/health` 必须快速返回

#### readiness（就绪）
- 额外检测：
  - DB 可写
  - AI 配置可读
  - 至少一个模型路由可用

#### deep-check（深度巡检，每5-15分钟）
- 冒烟任务：
  - 拉取少量数据
  - 触发一个轻量总结
  - 执行一次导出 dry-run

### 15.8 降级策略（保服务可用）

1. 模型全不可用：展示缓存 + 本地规则摘要
2. 数据源异常：展示上次快照并标记“数据滞后”
3. 导出失败：自动降级到简版导出
4. 发送网关异常：任务进入待发送队列，不丢消息

### 15.9 告警与值班策略（最小可用）

触发条件：
1. 连续 3 次健康检查失败
2. 10 分钟内重启超过阈值
3. P0 错误码出现（`SYS-*`, `DB-*`, `RTR-STATE-001`）

通知级别：
1. P0：实时通知（必须确认）
2. P1：聚合通知（5 分钟窗口）
3. P2/P3：日报汇总

### 15.10 D4 验收标准

1. 不再出现“启动成功但不可访问”未识别场景
2. 进程异常退出可自动恢复（恢复时间 <= 10 分钟）
3. `status` 可准确识别 unhealthy 状态
4. 启动失败能输出明确错误码与恢复建议
5. 连续 24 小时冒烟巡检通过率 >= 99%

### 15.11 D5 输入（周评审）

1. D1-D4 产物汇总为《P0稳定性基线报告 v1》
2. 输出 Top5 高风险项与对应 owner
3. 形成 Week2 治理执行顺序（D6-D10）

- 影响：AI总结中断或降级（P1）
- 现状：有路由基础，需强化熔断和回退可观测
- owner：AI 平台
- 目标截止：P0 Week2

3. **R3 大批量拉取/渲染导致前端卡顿与无响应**
- 风险分：`16`（4×4）
- 现象：3天大批量数据加载时页面交互变慢
- 影响：用户感知“系统崩溃”（P1/P2）
- 现状：已有局部优化，缺完整拆批与进度治理
- owner：前端工程
- 目标截止：P0 Week2

4. **R4 多数据源字段不一致导致归并误差**
- 风险分：`15`（3×5）
- 现象：事件去重/主题归并出现错配
- 影响：观点质量下降（P1）
- 现状：当前以规则为主，缺统一事件层主键
- owner：数据工程
- 目标截止：P1 Week1

5. **R5 导出链路样式依赖波动导致失败率上升**
- 风险分：`12`（3×4）
- 现象：样式函数/第三方脚本导致导出异常
- 影响：对外汇报材料不可用（P2）
- 现状：已有 safeMode，需稳定降级链路
- owner：前端工程
- 目标截止：P0 Week2

### 16.4 Owner 角色建议
- 后端稳定性 owner：启动、健康、任务状态机、重试
- AI 路由 owner：通道权重、熔断、回退、trace
- 前端稳定性 owner：大数据渲染、导出、交互反馈
- 数据质量 owner：字段标准化、事件归并、去重
- 产品 owner：SLO 审核、周报复盘、优先级决策

## 17. D6 交付：数据源拉取稳定性治理 v1

### 17.1 目标
- 让各数据源拉取“可预测、可重试、可去重、可降级”。
- 避免“拉取半小时无反馈/重复拉取/数据断档”。

### 17.2 统一拉取契约（所有数据源）

每次拉取任务必须输出：
1. `source`：`chatlog/email/news/media/mp/langbot/ext`
2. `run_id`：本次拉取唯一标识
3. `window_from/window_to`：拉取时间窗
4. `cursor_before/cursor_after`：游标前后值
5. `fetched_count/inserted_count/updated_count/skipped_count`
6. `duration_ms`
7. `status`：`success/partial/failed`
8. `error_code`（失败或部分成功时必填）

### 17.3 超时预算（Timeout Budget）

按源定义单次请求超时（建议初值）：
1. `chatlog`：10s（列表接口）/ 20s（全量窗口）
2. `email`：20s（IMAP 批次）
3. `news`：8s
4. `media/mp`：10s（本地文件或DB读取）
5. `langbot/ext`：8s

任务级超时：
1. 增量拉取任务：60s
2. 全量拉取任务：300s（可分片）

超时即触发 `ING-TIMEOUT-001`，进入重试策略。

### 17.4 重试策略（拉取专用）

可重试错误：
- `TIMEOUT/UNAVAILABLE/RATE/NET`

不可重试错误：
- `AUTH/VALIDATION`

重试参数：
1. 最大 3 次（含首次）
2. 退避：`1s -> 3s -> 7s`
3. 同一源并发重试不超过 1（防止雪崩）
4. 连续失败达到阈值进入冷却窗口（5-15分钟）

### 17.5 幂等与去重策略

#### 记录级幂等键
- 基础键：`source + raw_id + event_time(+sender/target)`  
- 无 `raw_id` 源：使用 `content_hash + normalized_time_bucket`

#### 任务级幂等键
- `source + cursor + window_from + window_to`

规则：
1. 已存在同幂等键记录：`skip` 或 `update`（按版本号/更新时间）
2. 禁止同一时间窗并发全量任务
3. 全量与增量冲突时：全量优先，增量挂起

### 17.6 游标策略（防断档）

1. 每源维护独立游标：`last_success_cursor`
2. 仅在 `success/partial(可接受)` 后推进游标
3. 失败时不推进游标，避免丢数
4. 支持回放窗口：最近 `N` 小时重扫（默认 24h）

### 17.7 分片与背压（大数据量）

1. 大时间窗按天/小时分片拉取
2. 单片处理完成才推进到下一片
3. 触发背压条件：
   - 写库延迟升高
   - 前端查询 P95 异常
4. 背压动作：
   - 降低拉取并发
   - 缩小单次分片大小

### 17.8 数据滞后监控（Lag）

每源计算：
1. `source_lag_minutes = now - latest_event_time`
2. `sync_gap_count = expected - actual`（可估）

分级告警：
1. 轻度滞后：>30 分钟（P2）
2. 中度滞后：>2 小时（P1）
3. 严重滞后：>6 小时（P0）

### 17.9 降级策略（拉取链路）

1. 单源失败：标记该源滞后，其他源继续
2. 多源失败：进入“只读 + 历史快照”模式
3. chatlog 失败：保留本地 DB 最近可用数据并显式提示
4. email 失败：停止自动轮询，仅允许手动重试
5. news/media/mp 失败：保留上次快照并标注“更新时间”

### 17.10 数据质量护栏

1. 拉取后最小校验：
   - 时间字段可解析
   - 主体字段非空（sender/title/content 之一）
2. 脏数据处理：
   - 进入隔离区（quarantine）
   - 不进入主列表
3. 质量指标：
   - `invalid_rate`
   - `duplicate_rate`
   - `late_arrival_rate`

### 17.11 D6 验收标准

1. 任一数据源失败不影响其他源继续拉取
2. 拉取任务可观测（run_id + cursor + counts + error_code）
3. 断网/超时场景下可自动重试并恢复
4. 不出现大规模重复入库
5. 页面可见“拉取进度/滞后状态”，避免无反馈等待

### 17.12 D7 输入（模型路由治理）

D6 输出将为 D7 提供：
1. 可用数据新鲜度指标（决定是否触发总结）
2. 分源健康状态（影响路由权重与降级策略）
3. 失败码分布（用于路由熔断阈值调优）

## 18. D7 交付：模型路由稳定性治理 v1

### 18.1 目标
- 让模型调用在高并发下“不断档”：主通道异常时自动补位，避免总结中断。
- 把路由从“静态权重”升级为“稳定性优先的动态调度”。
- 在不牺牲稳定性的前提下逐步优化成本与速度。

### 18.2 当前基线（按现配置）

> 基于现有配置快照（2026-03-07）：
1. `main_channels`：当前仅 `main-mm-m25` 启用（其余主通道保留但禁用）
2. `mid_channels`：5 个启用，等权
3. `tool_channels`：6 个启用，分层权重
4. `dynamic_weighting` 已启用（后端已有 runtime metrics 与 trace 能力）

结论：
- 主链路稳定性高度依赖 `main-mm-m25` 单点，需要“热备可切换机制”。

### 18.3 路由治理原则

1. **稳定性第一**：成功率优先于速度，速度优先于成本
2. **渐进式放量**：新通道先灰度，达标后升权
3. **失败隔离**：单通道失败不拖垮全模块
4. **可回滚**：任何调权/切换都可快速回退

### 18.4 路由决策因子（评分模型）

每个通道实时得分建议：
`score = base_weight × success_factor × latency_factor × concurrency_factor × breaker_factor`

- `base_weight`：配置基础权重
- `success_factor`：近窗口成功率（如近 50 次）
- `latency_factor`：对 `P95` 延时惩罚
- `concurrency_factor`：按 inflight 压力折损
- `breaker_factor`：熔断状态强惩罚（冷却期接近 0）

### 18.5 熔断与恢复策略

#### 触发条件（建议）
1. 连续失败 `>= breaker_failures`（默认 3）
2. 或近窗口成功率跌破阈值（如 < 60%）
3. 或超时率持续超阈值（如 > 40%）

#### 熔断动作
1. 通道进入 `cooldown`（默认 60-180s）
2. 该通道从候选池临时剔除
3. 任务自动切下一个可用通道

#### 恢复机制
1. 冷却结束后进入半开（small canary）
2. 通过连续 `N` 次成功后恢复正常权重
3. 半开失败则重新熔断并延长冷却

### 18.6 主/备/兜底通道策略（按 lane）

#### A. 主模型 lane（AI总结核心）
1. 主通道：`main-mm-m25`
2. 热备候选（当前禁用可随时启用）：
   - `main-sf-step35`
   - `main-sf-v3`
   - `main-or-trinity`
   - `main-gitee-qwen35-35b`
3. 策略：
   - 常态 100% 主通道
   - 主通道触发熔断时，按候选序列临时接管
   - 主通道恢复后回切（带观察窗口）

#### B. 中模型 lane（对话生成/中成本任务）
1. 初始等权（已启用）
2. 按稳定性分层：
   - 稳定层（保留高权）
   - 试验层（灰度流量）
3. 策略：固定留 10%-20% 流量做在线评估

#### C. 工具模型 lane（摘要抽取）
1. 保持多通道并发
2. 对高失败通道快速降权
3. 对低延迟高成功通道自动提权

### 18.7 流量分配与灰度机制

1. 新通道引入阶段：
   - `canary_ratio = 5%`
   - 连续 24h 达标后提升至 15%、30%
2. 达标门槛：
   - 成功率 >= 98%
   - P95 延时不劣于主通道 1.5 倍
   - 输出格式错误率 <= 1%
3. 不达标处理：
   - 自动降回 0%-5% 灰度

### 18.8 质量回写与自动调权

每次调用后回写：
1. `success/fail`
2. `latency_ms`
3. `error_code`
4. `output_validation_pass`

调权节奏：
1. 小步快调（每 5 分钟评估）
2. 大步调整需人工审批（避免振荡）
3. 可设置“权重冻结窗口”（重大行情日）

### 18.9 模块路由隔离（防串扰）

1. `route_key` 级隔离：`market/newswatch/meetings/...` 各自评估
2. 某模块失败不影响其他模块路由决策
3. 关键模块（market/newswatch）可配置更保守策略

### 18.10 观测面板（D7 必备）

按 lane + channel 展示：
1. 调用量、成功率、失败率、超时率
2. P50/P95/P99 延时
3. 熔断次数、冷却状态、恢复次数
4. 当前权重、动态得分、inflight

### 18.11 风险控制

1. 防单点：主 lane 不允许长期只有一个可用候选
2. 防雪崩：同故障码爆发时全局降并发
3. 防误判：调权需最小样本量门槛（如 >=30 次）
4. 防抖动：调权频率限制（例如 5 分钟一次）

### 18.12 D7 验收标准

1. 主通道异常时，任务不中断且自动补位成功
2. 熔断与恢复过程可观测且有日志证据
3. 72 小时内无“全通道不可用”中断事故
4. 路由调权后成功率不下降（或显著提升）
5. `route_key` 级隔离生效，单模块故障不扩散

### 18.13 D8 输入（导出稳定性治理）

D7 输出将为 D8 提供：
1. 导出模块的可用摘要质量保障（避免空结果导出）
2. 模型侧失败降级后的导出兼容要求
3. 错误码与告警联动（`MOD/RTR` -> `EXP`）
