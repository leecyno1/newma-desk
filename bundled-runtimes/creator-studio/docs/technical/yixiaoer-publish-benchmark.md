# 蚁小二发布运营机制学习与项目映射

- 来源：<https://yixiaoer.feishu.cn/docx/M2Add7W1DoxdvcxCyWmcGoJEn9g>
- 文档名称：`蚁小二-用户使用手册`
- 学习时间：`2026-07-20`
- 用途：作为第 7 环节 Publish 的产品机制基准，不把蚁小二作为本项目登录态或 Cookie 的直接依赖。

## 1. 核心产品模型

蚁小二不是单一上传器，而是把以下能力放进同一个运营工作台：

1. 账号资产：账号授权、创作者中心入口、账号分组、账号负责人、团队权限。
2. 发布执行：本机发布、浏览器自动填表、云端代理发布。
3. 批量生产：多视频对多账号的任务矩阵、批量表单、封面和文案继承。
4. 发布校验：按平台和账号差异校验必填字段，校验失败禁止发布。
5. 发布台账：保存团队与个人发布记录、发布详情和重新发布入口。
6. 运营维护：私信、评论、自动回复策略、成员协作。
7. 数据复盘：账号数据、作品数据、负责人数据和团队趋势。

文档称其支持 25+ 平台，视频批量任务最多可创建 80 个账号发布任务。这个数字只作为产品规模参考，不直接成为本项目硬编码上限。

## 2. 账号资产机制

### 2.1 授权与持久化

- 添加账号后在平台授权登录，完成后显式确认“我已完成登录”。
- 授权过程未加载完成时不能提前关闭，否则授权可能失败。
- 普通团队成员可以添加账号；管理员和创建人可以管理全部账号及运营权限。
- 账号运营人可以获得发文、进入创作者中心、重新授权、删除和备注账号等权限。

### 2.2 分组、负责人和预设

- 账号可以设置分组、运营人和负责人，数据权限随角色变化。
- 账号级可预设分类和话题，减少每次发布重复填写。
- 收藏和分组部分在文档中标记为维护中，不能视为稳定可用能力。
- “不掉线视频号”相关功能已标记下线，不能作为方案依据。

### 2.3 网络与地区

- 全局代理：授权、访问创作者中心、云发布全链路使用代理。
- 仅云发布代理：只在发布阶段使用代理。
- 默认代理仅支持有限地区和云发布；团队代理可覆盖授权、浏览器访问与云发布。
- 抖音、快手还存在账号位置配置。

本项目不能默认复制云代理模式。代理、位置和出口 IP 属于账号风控资产，必须按账号显式配置，并保留人工确认和风险说明。

## 3. 三种发布模式

| 蚁小二模式 | 含义 | Newma Publish 对应路线 |
| --- | --- | --- |
| 本机发布 | 使用当前电脑 IP 直接发布 | 本地 CLI、官方 API、`social-auto-upload` |
| 浏览器发布 | 打开官方创作者中心并自动填写表单 | 持久化 Chrome Profile + 浏览器确认 |
| 云端发布 | 使用账号配置的代理地区在云端发布 | 当前未实现，只保留为可选执行器类型 |

Newma Publish 继续坚持 API-first，但不能把“存在上传命令”误当成“发布成功”。所有路线都必须回收草稿 ID、平台 URL 或可验证回执。

## 4. 批量任务与表单继承

### 4.1 任务矩阵

蚁小二支持：

- 多视频发布到单账号。
- 单视频发布到多账号。
- 多视频发布到多账号。
- 一个视频对应一个账号；视频多于账号时可循环账号创建任务。

其核心不是一次命令传多个账号，而是先展开为独立待发布任务，再分别校验、执行和记录。

### 4.2 批量表单

- 默认封面取视频第一帧，也允许单独上传自定义封面。
- 默认标题可取第一个视频文件名，但部分平台不支持统一标题同步。
- 描述中的 `#话题` 在部分平台会转换成标签。
- 批量表单会覆盖已经生成的任务字段，因此需要明确字段继承优先级。

Newma Publish 应采用：全局批次默认值 → 平台默认值 → 账号预设 → 单任务覆盖。每个任务展开后必须拥有自己的最终字段快照，不能在执行时临时继承。

## 5. 平台表单校验

蚁小二按平台和账号归纳表单规则：

- 发布前检查必填项完整性与合规性。
- 平台或账号不同，字段和规则可以不同。
- 发现错误后禁止一键发布。
- 修正错误项后才能继续同步。

这与本项目的 Publish Guard 不同：

- `platform preflight` 负责发布前字段合法性。
- `Publish Guard` 负责发布后结果、链接、草稿 ID 和回执一致性。

两道 Gate 缺一不可。当前项目的发布前校验只覆盖标题、媒体文件等通用字段，尚缺小红书、抖音、B站、视频号、公众号的独立字段 Schema。

## 6. 发布台账与重新发布

蚁小二保存个人和团队发布记录，并支持查看详情与重新发布。本项目已有：

- `publish_result.json`
- `publish_verification_report.json`
- `publish_manifest.json`
- `publish_guard_report.json`
- 草稿、正式发布和人工验真状态区分

但“重新发布”尚未成为一等任务。后续应使用 `attempt_id` 建立新尝试，引用原任务与失败原因，禁止覆盖历史回执。

## 7. 运营与数据闭环

- 私信评论支持抖音、视频号等平台的统一管理和自动回复策略。
- 数据覆盖抖音、快手、小红书、视频号、B站、微博、头条号等账号和作品。
- 成员只能查看自己运营账号；负责人和管理员拥有更大范围的数据权限。
- 失效账号不更新数据；不同平台可提供的数据字段并不一致。

本项目已有 `post_publish_metrics` 契约和 Postmortem 阶段，但多数平台还没有稳定的数据采集器。未来必须保留平台原始字段，同时映射到统一指标，不得用空值或代理指标冒充平台真实数据。

## 8. 当前能力对照

| 能力 | 当前状态 | 结论 |
| --- | --- | --- |
| 多账号槽位 | 已实现 | `account_registry.json` 管理平台和槽位 |
| 安全登录态 | 已实现 | Browser Profile 与 CLI Session 分离，均不进入 Git |
| API/CLI/浏览器多路线 | 已实现 | 缺云代理路线，但不是当前必需项 |
| 账号分组、运营人、负责人 | 契约已实现 | 注册表已支持非敏感 alias、分组和矩阵角色，实际负责人待用户填写 |
| 账号级分类、话题预设 | 契约已实现 | `publish_presets` 已参与确定性字段继承，实际预设待按账号补充 |
| 多视频 × 多账号任务矩阵 | 已实现 | `expand_publish_matrix.py` 展开独立任务，Stage Publish 按 `task_id` 打包 |
| 平台级发布前表单校验 | 薄弱 | 当前只有通用字段检查 |
| 发布记录和验真 | 已实现 | 当前项目比蚁小二说明更严格 |
| 失败重新发布 | 已实现基础契约 | 追加 attempt 历史，并生成失败分类、指数退避和人工确认重试计划 |
| 账号/作品数据回收 | 契约存在 | 缺平台采集器和统一数据仓 |
| 私信评论和自动回复 | 未实现 | 作为后续运营阶段，不阻塞发布主线 |

## 9. 开发优先级

### P0：先补生产可靠性

1. 建立各平台发布字段 Schema 与发布前校验器。首版已由 `configs/publish/platform_form_rules.json` 和 `scripts/validate_publish_form.py` 落地。
2. 批量任务矩阵展开器已落地，每个平台、账号、素材组合生成独立任务。
3. 任务级 attempt、失败分类和退避计划已落地；下一步补账号发布窗口、频控和跨批次重新发布调度。

### P1：补账号运营资产

1. 为账号槽增加 `group`、`operator`、`owner`、`publish_presets`、`network_policy` 等非敏感字段。
2. 增加字段继承规则和最终字段快照。
3. 增加账号级发布频率、时间窗和失败退避策略。

### P2：补运营与数据

1. 接入账号数据、作品数据和负责人数据采集器。
2. 建立统一指标字典和平台原始字段存档。
3. 再评估评论、私信和自动回复，不与发布核心链耦合。

## 10. 不直接照搬的设计

- 不把 Cookie、密码或 API Secret 写入账号注册表。
- 不把云代理作为默认发布方式。
- 不以 CLI 返回码代替平台回执和验真。
- 不把“最多 80 个任务”写成固定业务限制。
- 不把已下线或维护中的功能列为当前依赖。
- 不允许批量任务共享一个模糊状态；每个任务必须独立校验、执行、回填和重试。
