# 基金研究投资分析引擎设计方案

**日期**: 2026-05-15  
**项目**: fund-analysis  
**定位**: 基金研究、投资分析、基金池管理与组合决策支持引擎

## 1. 设计目标

当前项目已经具备基金管理、基金经理管理、Wind/Tushare 数据同步、调研报告、AI 分析、评分筛选、Barra 暴露、Brinson 归因等能力。下一阶段不应继续堆叠页面，而应将系统升级为一个可持续迭代的基金研究投资分析引擎。

目标是构建一个从数据接入、指标计算、研究分析、基金筛选、基金池管理、组合诊断到投后跟踪的闭环系统。

核心原则：

1. **数据可信**：所有结论都能追溯到数据来源、更新时间、计算口径和证据材料。
2. **指标统一**：收益、风险、评分、归因、风格等指标必须由统一引擎计算，避免前后端口径漂移。
3. **研究可解释**：AI 报告不能只是自然语言总结，必须给出证据链、反方观点和监控触发器。
4. **决策闭环**：筛选不是终点，基金入池、观察、调仓、复盘、预警才是投研工作流的核心。
5. **渐进落地**：优先打通主链路，避免一次性重构过大。

## 2. 当前项目基础

### 2.1 已有前端能力

前端主要集中在 `app/(dashboard)`：

- 基金列表与详情
- 基金经理列表与详情
- 调研报告列表、上传和搜索
- AI 分析报告
- 基金筛选
- Wind 数据同步

这些页面已经覆盖投研系统的核心对象，但组织方式仍偏功能页面集合，尚未形成研究工作台。

### 2.2 已有后端能力

项目目前存在两套后端形态：

- `app/api`：Next.js API Routes，主要服务前端页面。
- `backend/main.py`：FastAPI 服务，承载基金、经理、评分、报告、筛选、Barra、Brinson、导出、数据同步等能力。

FastAPI 更适合作为研究计算主后端；Next.js API 更适合作为 BFF 或轻量页面接口。

### 2.3 已有数据模型

`prisma/schema.prisma` 中已经包含：

- `Fund`：基金主数据
- `Manager`：基金经理主数据
- `ResearchReport`：调研报告
- `AIAnalysisReport`：AI 分析报告
- `Score`：评分
- `ScreeningCriteria`：筛选模板
- `Holding`：持仓
- `HoldingFactor`：持仓因子
- `FactorExposure`：基金因子暴露
- `PerformanceAttribution`：业绩归因
- `ManagerProfile`：经理画像
- `PhilosophyTracking`：投资理念跟踪
- `FactorReturn`：因子收益
- `IndustryReturn`：行业收益

模型方向正确，已经具备升级为研究引擎的基础。

## 3. 主要问题

### 3.1 后端职责割裂

Next.js API 与 FastAPI 都承担业务逻辑，容易导致：

- 指标计算重复
- 字段命名不一致
- 错误格式不一致
- 缓存策略分散
- 权限与日志分散
- 前端调用链不清晰

建议将 FastAPI 收敛为研究计算主后端，Next.js 仅保留 BFF、页面聚合、上传代理、鉴权等职责。

### 3.2 数据血缘不足

目前已有数据表，但缺少系统化的数据版本与来源记录。投研系统必须知道：

- 数据来自 Wind、Tushare、人工录入还是报告抽取
- 数据采集时间
- 数据覆盖区间
- 是否存在缺失、异常、修正
- 指标基于哪个版本的数据计算

没有数据血缘，评分和 AI 结论很难被研究员信任。

### 3.3 评分体系偏静态

当前评分主要基于收益、风险、稳定性和管理能力，适合作为 v1。但真实投研还需要：

- 同类分位排名
- 相对基准超额收益
- 市场阶段适应性
- 风格漂移识别
- 规模变化影响
- 经理变更影响
- 归因后的能力识别

评分系统应输出分数、等级、得分解释、扣分项、数据缺口和更新日期。

### 3.4 AI 缺少强制证据链

AI 报告如果只生成自然语言，会出现不可验证的问题。投研报告应强制包含：

- 使用了哪些结构化指标
- 使用了哪些调研报告片段
- 哪些结论来自模型推理
- 哪些结论只是数据不足下的假设
- 反方观点是什么
- 后续需要跟踪什么指标

### 3.5 缺少基金池与组合闭环

筛选系统是入口，但投资流程需要：

1. 条件筛选
2. 进入候选池
3. 深度研究
4. 进入观察池或核心池
5. 组合配置
6. 持续预警
7. 定期复盘
8. 调仓或移出

当前系统还缺少基金池、组合、预警和复盘状态机。

## 4. 目标架构

建议采用五层架构。

### 4.1 数据接入层

负责接入和标准化外部数据：

- Wind/Tushare 基金主数据
- 净值序列
- 基金持仓
- 基金经理任职
- 基准指数
- 行业分类
- 因子收益
- 基金公告
- 调研纪要
- 人工上传文件

每次接入都生成数据快照，记录来源、时间、覆盖范围和异常信息。

### 4.2 数据资产层

负责保存清洗后的核心实体：

- 基金主数据
- 基金经理主数据
- 净值时间序列
- 持仓快照
- 报告原文与切片
- 基准和同类分组
- 指标快照
- AI 研究结论

数据资产层应稳定、可追溯、可重算。

### 4.3 研究计算层

负责统一计算所有研究指标：

- 收益指标
- 风险指标
- 回撤指标
- 滚动指标
- 同类分位
- 基准超额
- 持仓集中度
- 行业偏离
- 因子暴露
- Brinson 归因
- 基金经理能力画像
- 评分和评级

这一层建议完全由 FastAPI/Python 承担。

### 4.4 智能研究层

负责结合结构化数据和非结构化报告：

- 调研报告切片
- 向量检索
- 实体链接
- 观点抽取
- 经理言行一致性分析
- AI 深度报告
- 反方观点生成
- 后续跟踪问题生成

AI 输出必须绑定证据和数据截止日期。

### 4.5 投资决策层

负责研究成果转化为投资动作：

- 策略筛选模板
- 候选池
- 观察池
- 核心池
- 黑名单
- 组合构建
- 组合风险暴露
- 调仓建议
- 预警事件
- 研究复盘

这一层是项目从“分析工具”升级为“投资研究引擎”的关键。

## 5. 后端职责划分

### 5.1 FastAPI 主后端

FastAPI 应负责：

- 数据同步
- 数据清洗
- 指标计算
- 评分
- Barra/Brinson
- AI 报告生成
- 语义检索
- 批量任务
- 导出
- 基金池和组合分析

### 5.2 Next.js BFF

Next.js API Routes 应负责：

- 前端页面所需数据聚合
- 鉴权上下文
- 文件上传入口
- SSE/流式响应转发
- 前端友好的错误格式
- 避免浏览器直接暴露内部后端地址

### 5.3 数据库

PostgreSQL 作为主库，保存结构化实体、指标快照和工作流状态。向量库建议二选一：

- 如果部署简单优先：使用 PostgreSQL + pgvector。
- 如果报告规模大、检索压力高：使用 Qdrant。

不建议长期同时维护两套向量存储。

### 5.4 任务队列

引入 Redis + RQ/Celery/Arq，用于：

- 批量基金同步
- 净值增量更新
- 指标重算
- 报告解析
- Embedding 生成
- AI 报告生成
- 策略回测
- 预警扫描

## 6. 核心模块设计

### 6.1 数据同步中心

提供统一任务入口：

- 单基金同步
- 批量基金同步
- 基金经理同步
- 净值同步
- 持仓同步
- 基准指数同步
- 因子收益同步
- 报告导入

每个任务应有状态：`pending`、`running`、`success`、`failed`、`partial_success`。

### 6.2 指标工厂

指标工厂是研究引擎核心。它不应散落在页面或 API 中，而应统一为独立服务。

建议输出指标包括：

- 近 1 月、3 月、6 月、1 年、3 年、5 年收益
- 年化收益
- 年化波动
- Sharpe
- Sortino
- Calmar
- 最大回撤
- 回撤修复天数
- 胜率
- 月度正收益比例
- 滚动 1 年收益分位
- 滚动 Sharpe 分位
- 相对基准收益
- 信息比率
- 跟踪误差
- 上行/下行捕获率

所有指标保存到 `MetricSnapshot`，避免重复计算。

### 6.3 评分引擎

评分分为四层：

1. **绝对表现评分**：收益、回撤、波动、Sharpe。
2. **相对表现评分**：同类分位、基准超额、信息比率。
3. **风格与归因评分**：风格稳定性、选股贡献、行业配置贡献。
4. **研究调整评分**：经理变更、规模膨胀、持仓拥挤、报告负面信号。

输出结构应包含：

- 总分
- 等级
- 分维度得分
- 关键加分项
- 关键扣分项
- 数据缺口
- 计算日期
- 使用的数据快照版本

### 6.4 基金画像

基金详情页应形成完整画像：

- 基础信息
- 业绩表现
- 风险特征
- 同类排名
- 基准比较
- 持仓结构
- 行业偏离
- 因子暴露
- 风格漂移
- 归因分析
- 适合的市场环境
- 不适合的市场环境
- 研究结论和风险点

### 6.5 经理画像

经理画像应回答：这个经理到底擅长什么、不擅长什么、是否稳定。

建议维度：

- 任职历史
- 管理产品矩阵
- 历史业绩
- 能力圈
- 风格偏好
- 风格稳定性
- 逆境表现
- 规模管理能力
- 代表产品
- 调研观点一致性
- 近期变化

### 6.6 RAG 研究报告库

报告系统应从“搜索文档”升级为“研究证据库”。

处理流程：

1. 上传或导入报告。
2. 文档解析。
3. 元数据抽取。
4. 文本切片。
5. Embedding。
6. 实体链接到基金、经理、公司、行业。
7. 观点抽取。
8. 生成可引用证据。

检索结果应返回：

- 文档标题
- 片段内容
- 相似度
- 关联基金/经理
- 报告日期
- 来源
- 可用于 AI 报告的 citation id

### 6.7 AI 投研报告

AI 报告应从“自动写文章”升级为“证据驱动的投研结论”。

标准报告结构：

1. 投资结论
2. 核心理由
3. 业绩分析
4. 风险分析
5. 经理分析
6. 持仓与风格
7. 归因分析
8. 反方观点
9. 数据缺口
10. 后续跟踪触发器

AI 报告必须保存：

- prompt version
- model name
- data sources
- research reports used
- metric snapshot id
- generation params
- created at

### 6.8 基金池工作流

新增基金池能力：

- 候选池：筛选后待研究。
- 观察池：有亮点但证据不足。
- 核心池：通过研究，可用于组合。
- 黑名单：明确回避。

每个基金池成员应包含：

- 入池理由
- 入池人
- 入池日期
- 证据链接
- 当前状态
- 下次复查日期
- 触发条件
- 最新评分

### 6.9 组合分析

组合层支持：

- 组合持仓
- 权重
- 组合收益
- 组合回撤
- 基金间相关性
- 风格暴露
- 行业暴露
- 经理集中度
- 基金公司集中度
- 最大风险贡献
- 调仓建议

这部分可以在基金池稳定后再建设。

## 7. 数据模型增强建议

建议新增模型：

### 7.1 DataSourceSnapshot

记录每次数据采集：

- source
- dataset
- startedAt
- finishedAt
- status
- recordCount
- coverageStart
- coverageEnd
- errorMessage
- checksum

### 7.2 MetricSnapshot

记录基金或经理在某日的指标：

- targetType
- targetId
- asOfDate
- metricName
- metricValue
- metricUnit
- window
- benchmarkId
- peerGroupId
- sourceSnapshotId

### 7.3 Benchmark

记录基准指数：

- code
- name
- type
- provider
- description

### 7.4 PeerGroup

记录同类分组：

- name
- category
- rule
- description

### 7.5 FundPool / PoolMember

记录基金池和成员状态。

### 7.6 Portfolio / PortfolioHolding

记录组合及组合持仓。

### 7.7 ResearchInsight

记录人工或 AI 研究结论：

- targetType
- targetId
- conclusion
- thesis
- evidence
- risks
- confidence
- validUntil
- authorType
- authorId

### 7.8 AlertRule / AlertEvent

记录预警规则和触发事件。

### 7.9 BacktestRun

记录筛选策略或组合策略回测结果。

## 10. 成功标准

阶段性成功标准：

1. 任意基金详情页能展示数据截至日期、指标口径和数据来源。
2. 任意评分结果能解释得分原因和扣分原因。
3. 任意 AI 报告能追溯到结构化指标和报告证据。
4. 筛选结果能进入基金池，并记录入池理由。
5. 基金池成员能触发预警和复盘任务。
6. 组合页面能解释组合的主要风险来源。

最终目标是让系统回答三个核心问题：

1. 这个基金为什么值得研究？
2. 这个基金为什么值得买或不值得买？
3. 买入之后应该跟踪什么，什么时候需要重新评估？
