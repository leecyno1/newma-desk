# 基金研究引擎架构决策记录

**日期**: 2026-05-15  
**状态**: Proposed  
**项目**: fund-analysis  
**决策范围**: 后端职责划分、API 所有权、研究计算边界、迁移策略

## 1. 背景

当前项目同时存在两类 API 层：

1. `app/api` 下的 Next.js API Routes。
2. `backend/routes` 下的 FastAPI Routes。

两者都承担了一部分基金、经理、报告、筛选、评分、同步等业务职责。这种结构在原型阶段可以快速推进，但如果项目继续升级为基金研究投资分析引擎，会产生以下问题：

- 同一类业务在两处实现，口径容易不一致。
- 指标计算散落在 TypeScript 和 Python 中，难以保证结果一致。
- AI、向量检索、Barra、Brinson、批处理更适合 Python 生态，但前端 API 也在承担部分逻辑。
- 数据同步、指标快照、评分解释、基金池、组合分析需要统一后端状态管理。
- 未来接入队列、缓存、数据血缘和任务中心时，需要清晰的服务边界。

因此需要明确：谁是研究计算权威后端，谁负责前端页面聚合。

## 2. 决策

### 2.1 FastAPI 作为研究计算主后端

FastAPI 是基金研究引擎的权威后端，负责所有需要稳定口径、可追溯和可复算的业务。

FastAPI 拥有以下职责：

- 基金主数据查询和同步
- 基金经理主数据查询和同步
- 净值、持仓、基准、行业、因子数据同步
- 数据同步任务状态和数据血缘
- 指标计算和指标快照
- 评分和评级
- Barra 风格暴露
- Brinson 业绩归因
- 调研报告解析、切片、Embedding、语义检索
- AI 投研报告生成和证据链保存
- 筛选策略执行
- 基金池状态流转
- 预警扫描
- 组合诊断
- 回测任务
- 数据导出

所有能影响投资研究结论的计算逻辑，都应以 FastAPI/Python 为唯一权威来源。

### 2.2 Next.js 作为 UI 与 BFF

Next.js 的主要职责是页面渲染、交互和前端友好的聚合接口。

Next.js API Routes 可以保留以下职责：

- 代理浏览器到 FastAPI 的请求，隐藏内部后端地址。
- 处理前端会话、鉴权、权限上下文。
- 文件上传入口和上传前校验。
- SSE 或流式响应转发。
- 为特定页面聚合多个 FastAPI 响应。
- 对前端统一错误格式和 loading 体验。
- 与 Next.js 页面强绑定的轻量操作。

Next.js 不应长期承担以下职责：

- 指标计算
- 评分计算
- 筛选核心逻辑
- AI 报告核心生成逻辑
- 数据同步核心逻辑
- 数据血缘写入
- 向量检索核心逻辑
- Barra/Brinson 计算
- 基金池状态机规则
- 组合风险计算

### 2.3 PostgreSQL 作为主业务数据库

PostgreSQL 继续作为结构化数据主库。所有研究结论、指标快照、基金池状态、任务状态、组合状态都应落库。

向量存储需要后续单独决策。短期可以保留现有实现，但中期必须明确 pgvector 或 Qdrant 作为主存储，避免两套检索逻辑长期并存。

### 2.4 任务队列作为异步执行层

批量同步、指标重算、Embedding、AI 报告、预警扫描、回测不应长期在请求线程内完成。

后续应引入任务队列，例如 Redis + RQ/Celery/Arq。队列不是 Phase 0 的直接实施目标，但所有新接口设计应预留任务化能力。

## 3. API 所有权原则

### 3.1 FastAPI Owned

满足任一条件即归 FastAPI：

- 需要访问或更新研究数据库状态。
- 需要计算指标或评分。
- 需要调用 Wind/Tushare 等数据源。
- 需要调用 AI 或向量检索。
- 需要产生可审计研究结论。
- 需要异步任务或批处理。
- 需要被其他系统复用。

### 3.2 Next.js BFF Owned

满足以下条件才归 Next.js：

- 强依赖页面交互形态。
- 只是聚合或转发 FastAPI 响应。
- 不产生权威研究结果。
- 不保存核心业务状态，或只保存前端会话状态。
- 需要利用 Next.js runtime 的 SSR、cookies、headers 或 streaming 能力。

### 3.3 Temporary Duplicate

当前重复 API 不立刻删除，而是按以下方式迁移：

1. 先完成 API inventory。
2. 标记重复逻辑和权威目标。
3. 为 FastAPI 补齐缺失能力。
4. Next.js API 改为代理或聚合。
5. 前端调用稳定后删除重复计算逻辑。

## 5. 迁移策略

### 5.1 不破坏现有页面

短期内不直接删除 `app/api` 的现有接口。迁移采用兼容策略：

- 保留原 URL。
- 内部实现逐步改为调用 FastAPI。
- 响应结构保持前端兼容。
- 新能力优先直接加在 FastAPI。

### 5.2 先新增后替换

对于数据血缘、指标快照、基金池等新能力，直接在 FastAPI 实现。前端新页面或新模块优先调用 FastAPI/BFF 聚合接口。

### 5.3 先读后写

迁移顺序：

1. 先迁移只读查询。
2. 再迁移计算接口。
3. 最后迁移写入和状态流转接口。

### 5.4 每个迁移单元都要可回滚

每次迁移应满足：

- 旧接口仍可恢复。
- 新接口有 smoke test。
- 前端有 loading/error fallback。
- 日志能区分请求走旧逻辑还是新逻辑。

## 6. 风险与应对

### 6.1 风险：FastAPI 与 Prisma 数据访问割裂

当前 Next.js 通过 Prisma 访问数据库，FastAPI 通过 Python repository 访问数据库。后续如果两个栈都直接写库，仍可能产生口径问题。

应对：

- 核心写入统一走 FastAPI。
- Prisma 主要用于 schema 管理和前端必要查询。
- 对关键表建立 repository 层，避免散落 SQL。

### 6.2 风险：迁移期间接口数量增加

短期会出现旧 Next API、新 FastAPI、BFF 代理共存。

应对：

- 维护 `docs/plans/api-inventory.md`。
- 每个 endpoint 标注 owner 和 migration status。
- 不允许新增无 owner 的业务 API。

### 6.3 风险：AI 报告输出格式不稳定

AI 输出如果没有结构化 contract，会影响前端和存储。

应对：

- 先定义报告输出 contract。
- 模型输出后做结构校验。
- 不合格时走 fallback 或返回可恢复错误。

### 6.4 风险：指标历史重算成本高

随着基金和净值数据增加，实时计算会变慢。

应对：

- 使用 `MetricSnapshot`。
- 增量计算优先。
- 批量重算进入任务队列。

## 7. 验收标准

该 ADR 被采纳后，应满足：

1. 所有新增研究计算能力默认放入 FastAPI。
2. Next.js API 不再新增核心计算逻辑。
3. 每个 API endpoint 都能在 inventory 中找到 owner。
4. 评分、指标、AI、筛选、基金池等模块有明确迁移路径。
5. 后续开发计划可以围绕 FastAPI 主后端逐步实施。

## 8. 后续行动

1. 生成 API inventory。
2. 标记重复接口和迁移目标。
3. 从数据血缘和指标快照开始实施。
4. 将评分接口迁移到基于指标快照的 FastAPI 权威计算。
5. 将 AI 报告升级为证据链报告。
